## (a) Pontos que JÁ têm medição real de tempo

| Onde | O que mede | Formato |
|---|---|---|
| `_voice_turn_started` (ipc_handlers.py:2218) + `_voice_elapsed_ms()` (linha 1140-1143) | Relógio cumulativo desde o início do turno de voz | usado nos prints `[VOICE_TRACE] ... ms=` |
| `[VOICE_TRACE] stage=WAKE_EVENT/WAKE_GATE/STT_RESULT/NORMALIZED_TEXT` | Marcos de chegada de voz (sem duração própria, só timestamp cumulativo quando presente) | print |
| `[VOICE_TRACE] stage=INTENT_MATCH result=START ms=...` (linha 2316-2319) | Timestamp cumulativo **na entrada** do bloco PC-intent (antes de `_try_compound_pc_intent`) | print |
| `[VOICE_TRACE] stage=ACTION_DISPATCH result=COMPLETED ms=...` (linha 2324-2327) | Timestamp cumulativo **na saída** do bloco PC-intent (depois de `_try_compound_pc_intent` + `_try_pc_intent`) | print |
| `[VOICE_TRACE] stage=FINAL_RESPONSE ... total_ms=...` (linha 2337-2341) | Timestamp cumulativo depois do TTS ter sido disparado | print |
| `_tts_started` / `[VOICE_TRACE] stage=TTS_START result=PASS ... ms=...` (linha 2745-2822) | Duração real e isolada do TTS (engine, retry, fallback) | print, com delta próprio (não cumulativo) |
| `ActionRegistry.execute()` / `execute_async()` (action_registry.py:401-508) | Duração real de **cada execução de action individual** (`duration_ms` gravado em `ActionResult`) | **calculado mas nunca impresso/logado** — ver (b) |
| `_executar_intent_de_pc` (ipc_handlers.py:1684, `started = time.perf_counter()`) | Só usado dentro do `except` via `_observe_failure` → `[OBS] ... duration_ms=` | **só loga em caminho de exceção, nunca no caminho de sucesso** |
| `backend_startup` (linha 4469-4479) | Tempo de boot do processo backend | `[OBS] action=backend_startup ... duration_ms=` |

**Conclusão de (a):** existe instrumentação real de tempo, mas ela é toda de **borda externa**
(início do turno → primeira checagem de intent → fim da checagem de intent → fim do TTS).
Não existe nenhum ponto que meça o que acontece **dentro** dessa janela quando o comando é composto.

`core/model_router.py` **não tem nenhuma medição de latência**. Os três usos de `time.time()`
encontrados (linhas 484, 518, 535) são todos para janelas de cooldown/saúde de provedor
(`HealthState.COOLDOWN`, `EXHAUSTED` etc.) — controlam *quando* um modelo volta a ficar
disponível depois de um erro, não quanto tempo uma chamada de modelo levou. Além disso,
`_try_compound_pc_intent` é 100% determinístico (regex + `PcVoiceIntentDetector`) e nunca
chama `model_router`/LLM — então, para este comando específico, o roteador de modelo está
fora do caminho crítico. Ele importa para latência em *outros* fluxos (conversa livre), não
neste.

## (b) Pontos cegos — sem NENHUMA medição

Foco pedido: `_try_compound_pc_intent` (ipc_handlers.py:1966-2023).

**Confirmado por leitura: só existe um tempo total, nenhuma etapa individual tem timestamp.**

```python
outcomes: list[str] = []
for index, part in enumerate(parts, start=1):
    reply = await self._try_pc_intent(part)          # <- nenhum timestamp antes/depois
    outcomes.append(f"{index}) {reply or 'Etapa não executada.'}")
return "Resultado por etapa: " + " ".join(outcomes)
```

O único par de marcadores que envolve essa função inteira é o `INTENT_MATCH result=START` /
`ACTION_DISPATCH result=COMPLETED` da chamada (linhas 2316-2327) — e esse `ms=` é **cumulativo
desde o início do turno de voz**, não um cronômetro dedicado a essa etapa. Isso dá o custo
total das N sub-ações juntas, mas não diz:

- quanto tempo cada cláusula (`abra o youtube`, `pesquise X`, `toque`) levou individualmente;
- se o tempo foi gasto na detecção de intent (`PcVoiceIntentDetector.detect`, puro regex) ou
  na execução real da ação (I/O com o Windows/navegador);
- em qual das N etapas o gargalo mora quando o comando composto é lento.

Outros pontos cegos confirmados:

1. **`ActionRegistry.execute_async` já calcula `duration_ms` por action (linha 496), mas
   ninguém lê esse campo.** Busquei `duration_ms` em todo `ipc_handlers.py`: as duas únicas
   ocorrências são o `_observe_failure` (caminho de exceção) e o `backend_startup`. O valor
   que o próprio ActionRegistry calcula para cada execução bem-sucedida é descartado — dado
   que já existe, só não é logado.
2. **`_executar_intent_de_pc` cronometra (`started = time.perf_counter()`, linha 1684) mas só
   usa esse cronômetro dentro do `except` (linha 1963).** No caminho feliz (a maioria dos
   casos), o tempo gasto detectando e roteando o intent nunca aparece em log nenhum.
3. **Os loops de polling de UI Automation em `core/actions/media_apps.py` não medem quanto
   tempo realmente ficaram esperando** — só retornam sucesso/falha booleano depois de rodar
   até um `timeout`. Especificamente para o "toque" do exemplo do Alex:
   - `_find_youtube_video_result` (media_apps.py:443-487): timeout de **8.0s**, faz
     `automation.GetRootElement()` (raiz do **desktop inteiro**, não escopada à janela do
     navegador) e `FindAll` a cada iteração, dormindo `time.sleep(0.2)` entre tentativas.
   - `_ensure_youtube_playing` (media_apps.py:557 em diante): timeout de **10.0s**.
   - `_find_youtube_skip_button` / `_find_youtube_button`: timeout de 1.5s cada.
   Nenhuma dessas funções loga quantas iterações rodou ou em qual iteração encontrou o
   elemento — só existe "achou" ou "não achou depois do timeout inteiro".
4. **`_send_url_to_default_browser`** (os_ops.py:299-344, usada por `youtube_open` e
   `youtube_search`) faz `os.startfile(url)` e um `time.sleep(0.35)` fixo, depois verifica
   só se **algum** processo de navegador está rodando — não espera nem mede quanto tempo o
   navegador levou para de fato abrir/renderizar a página. Se o navegador estava fechado
   (partida fria), esse tempo real de subida do processo não é medido em lugar nenhum.

## (c) Hipóteses (INFERIDO — não medi rodando o app, só li o código)

**INFERIDO-1 — o gargalo do comando composto está majoritariamente na etapa "toque", não no despacho.**
`youtube_play_by_name_action` (media_apps.py:814-846) encadeia `youtube_search_action`
(sleep fixo de 0.35s) → `_find_youtube_video_result` (poll de até 8s, varrendo UI Automation)
→ `.invoke()` → `_ensure_youtube_playing` (poll de até 10s). Como o loop do compound é
sequencial e cada etapa usa `await` bloqueante até terminar, se a página do YouTube ainda não
carregou quando o poll de 8s começa, a ZARA fica muda por vários segundos sem nenhum log
intermediário, e é exatamente a etapa final ("toque") do exemplo do Alex.

**INFERIDO-2 — a varredura de UI Automation parte do desktop inteiro, não da janela do navegador.**
`_find_youtube_video_result` chama `automation.GetRootElement()` (raiz de todo o desktop) e
`FindAll(TreeScope_Descendants, ...)` a partir dali, repetindo isso a cada 0.2s até 8s. Isso é
uma varredura de árvore de acessibilidade do **sistema operacional inteiro**, não só da aba do
YouTube. Com mais janelas/abas abertas no PC do Alex, cada iteração desse `FindAll` pode ficar
sensivelmente mais lenta — mas como ninguém mede a duração de uma iteração isolada, não dá
para saber se isso é responsável por 200ms ou por vários segundos por chamada.

**INFERIDO-3 — custos fixos de sleep somam linearmente com o número de cláusulas.**
Cada etapa que abre/envia URL ao navegador tem um `time.sleep(0.35)` fixo
(`_send_url_to_default_browser`), e várias sub-rotinas de mídia têm sleeps de 0.1–0.25s
adicionais. Isso sozinho já soma ~0.7–1s fixos de espera "cega" só para 2 das 3 etapas do
exemplo (abrir + pesquisar), antes de qualquer polling de conteúdo. Quanto mais cláusulas o
comando composto tiver, mais esse custo fixo cresce de forma linear e é 100% previsível — mas
hoje invisível, porque não há log por etapa.

**Instrumentação mínima recomendada antes de testar** (sem isso, os 3 testes abaixo só vão dar
um número total, igual ao que já existe hoje):

2. Em `youtube_play_by_name_action` (media_apps.py:814), logar a duração real de

   por exemplo `elapsed = time.monotonic() - deadline_start` no ponto em que cada uma retorna.
3. Surfacear o `duration_ms` que `ActionRegistry.execute_async` já calcula (action_registry.py:496)
   em vez de descartá-lo — bastaria logar `result.duration_ms` no ponto em que `_try_pc_intent`
   recebe o `ActionResult`.

Sem (1)-(3), os testes físicos abaixo só confirmam ou refutam a hipótese **por comparação de
tempo total entre variações do comando**, nunca por número exato de onde o tempo foi — mas já
servem para decidir se vale a pena instrumentar antes de mexer em código de produção.

---

**TESTE 1 — isolar a etapa "toque" (confirma/refuta INFERIDO-1)**

Falar, cronometrando do fim da fala até o início da resposta falada:

1. `"Zara, abra o youtube."` (sozinho)
2. `"Zara, pesquise [algo] no youtube e toque."` (2 cláusulas, sem o "abra" solto)
3. `"Zara, abra o youtube, pesquise [algo] e toque."` (as 3 cláusulas, igual ao relato do Alex)

Se o tempo de (3) for muito maior que a soma aproximada de (1)+(2), o gargalo está mais na
interação entre etapas (ex.: página não carregou ainda quando "pesquise" roda) do que em cada
etapa isolada. Se (2) sozinho já for quase tão lento quanto (3), o "toque" (busca+play) é
mesmo o vilão, confirmando INFERIDO-1.

**TESTE 2 — navegador frio vs quente (confirma/refuta INFERIDO-1 e parte do INFERIDO-3)**

1. Fechar completamente o navegador padrão. Falar o comando composto completo do Alex.
   Cronometrar do fim da fala até a resposta falada.
2. Com o navegador já aberto (uma aba qualquer visível), repetir a mesma frase exata.
   Cronometrar de novo.

Se (1) for visivelmente mais lento que (2), parte do tempo é o processo do navegador subindo
do zero — tempo que hoje não é esperado nem medido por `_send_url_to_default_browser`
(só dorme 0.35s fixos e seque em frente).

**TESTE 3 — custo da varredura de UI Automation (confirma/refuta INFERIDO-2)**

Com o PC do Alex no estado normal de uso dele (várias janelas/abas abertas, como costuma
estar), falar o comando composto completo duas vezes:

1. Com só o navegador aberto (fechar outros apps pesados, ex. editores, Electron apps).
2. No estado normal do dia a dia dele (tudo aberto como sempre).

Se (2) for perceptivelmente mais lento que (1) na mesma máquina, a varredura de UI Automation
a partir da raiz do desktop (INFERIDO-2) ganha peso como causa real, porque mais elementos na
árvore de acessibilidade do sistema tornam cada `FindAll` mais caro.

## WHAT_IS_PROVEN / WHAT_IS_INFERRED / WHAT_IS_UNKNOWN

**WHAT_IS_PROVEN** (por leitura de código, não por execução):
- `_try_compound_pc_intent` não tem nenhum timestamp por etapa, só o par
  INTENT_MATCH/ACTION_DISPATCH cumulativo ao redor da chamada inteira.
- `ActionRegistry` calcula `duration_ms` por action mas esse valor nunca é logado no caminho
  de sucesso.
- `_executar_intent_de_pc` só loga tempo no caminho de exceção.
- `model_router.py` não mede latência de chamada nenhuma; seus `time.time()` são para
  cooldown de saúde de provedor.
- `_find_youtube_video_result` e `_ensure_youtube_playing` têm timeouts de polling de 8s e
  10s respectivamente, sem log de duração real.

**WHAT_IS_INFERRED** (rotulado acima como INFERIDO-1/2/3): que o gargalo do comando composto
do exemplo está concentrado na etapa "toque" (busca + seleção + confirmação de play via UI
Automation), possivelmente agravado por varredura de árvore de acessibilidade não escopada e
por sleeps fixos somando linearmente. Nenhuma dessas três hipóteses foi medida rodando o app.

**WHAT_IS_UNKNOWN**:
- Quanto tempo, em número real, cada cláusula do exemplo do Alex leva hoje no PC dele.
- Se a lentidão reportada é reproduzível sempre ou só em certas condições (navegador frio,
  muitas janelas abertas, rede lenta ao carregar a página de resultados do YouTube).
- Se existe algum outro caminho (ex. `_try_jarvis_multi_action`, que exige Supercérebro ativo)
  sendo acidentalmente acionado em vez do `_try_compound_pc_intent` determinístico — não
  verifiquei se a frase exata do Alex bate com 3 domínios do `_try_jarvis_multi_action" e
  dispara aquele caminho em vez deste; se disparar, o comportamento e o custo são outros.
